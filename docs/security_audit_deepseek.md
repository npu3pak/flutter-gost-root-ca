## 1. Исполнительное резюме

Плагин решает задачу совместимости: сайты с гостовскими TLS-цепочками
(например, www.sberbank.ru) не проходят проверку сертификата, потому что
их корневой центр (НУЦ Минцифры России, **Russian Trusted Root CA**) не
входит в системные хранилища доверенных корней iOS и Android.

Механизм добавляет этот единственный корень в **все** точки проверки
сертификатов приложения. Валидация TLS при этом **не отключается**:
сначала сертификат оценивается стандартно (системные корни), и только при
неуспехе — повторно с добавленным корнем Минцифры. SSL-pinning и mTLS
хост-приложения сохраняются.

Ключевые изменения в безопасности:

| № | Что меняется | В какую сторону |
|---|---|---|
| 1 | В модель доверия приложения добавляется корневой CA Минцифры (глобально, для всех доменов и всех стеков) | **Риск растёт**: возможности MITM получает один дополнительный CA, его суб-ЦА и их компрометация |
| 2 | На iOS требуется глобальное отключение ATS (`NSAllowsArbitraryLoads=true`) | **Риск растёт значительно**: разрешён незашифрованный HTTP и сняты требования ATS к TLS для всего трафика приложения, а не только для гостовских цепочек |
| 3 | Глобальные перехваты: `HttpOverrides.global`, method swizzling `URLSession`/`WKWebView`, Network Security Config для всех доменов | **Риск растёт умеренно**: техники процесса-wide, влияют на все плагины/SDK внутри приложения; предсказуемость снижается, возможны конфликты |
| 4 | Стандартная проверка сертификата остаётся первой; проверка hostname не ослабляется; pinning/mTLS не ломаются; данные не логируются | **Риск не меняется / частично снижается** |

**Главный вывод для решения:** использование плагина эквивалентно решению
«доверять приложению TLS-сертификаты, выпущенные НУЦ Минцифры, для любых
доменов» плюс отключение ATS на iOS. Для приложений, которым гостовские
цепочки не нужны, применение плагина **не рекомендуется**. Для
приложений с реальной потребностью (доступ к гостовским ресурсам) риск
приемлем при выполнении рекомендаций раздела 6, прежде всего —
ограничения области действия и отдельного решения ИБ по ATS.

## 2. Описание механизма (для отдела ИБ)

### 2.1. Проблема, которую решает плагин

Операционная система проверяет HTTPS-сертификат сайта по списку встроенных
доверенных корней. Гостовские сайты используют корень **Russian Trusted
Root CA** (НУЦ Минцифры России), которого в системных списках нет, —
поэтому проверка не проходит и соединение обрывается. Стандартные сайты
(яндекс, google) работают, их корни в системе есть.

### 2.2. Состав механизма

| Компонент | Что делает | Файлы |
|---|---|---|
| `GostRootCa.enable()` | Единственная точка входа; настраивает dart:io и нативную сторону | `gost_root_ca/lib/gost_root_ca.dart` |
| `GostHttpOverrides` | Глобальный `HttpOverrides.global` для dart:io: хранилище доверенных корней = системные корни + корень Минцифры | `gost_root_ca/lib/src/gost_http_overrides.dart` |
| iOS `GostSslSwizzler` | Method swizzling `URLSession` и `WKWebView`; перехват server trust challenge; повторная оценка с якорем Минцифры | `gost_root_ca_ios/ios/Classes/GostSslSwizzler.swift` |
| iOS ATS-исключение | Требуемый хост-приложением ключ `NSAllowsArbitraryLoads=true` в `Info.plist` (сам плагин редактировать его не может) | README.md, `example/ios/Runner/Info.plist` |
| Android Network Security Config | Декларативный список доверенных корней для всех нативных стеков: `system` + корень Минцифры; вливается в манифест хоста при сборке | `gost_root_ca_android/android/src/main/res/xml/gost_network_security_config.xml`, `AndroidManifest.xml` |
| Встроенный корень | PEM-константа в **трёх** копиях (dart, Swift, raw-resource Android); самоподписанный, RSA 4096/SHA-256, серийный номер 1000, срок действия 01.03.2022 — 27.02.2032 | `gost_root_ca/lib/src/gost_root_cert.dart`, `GostBuiltinRootCert.swift`, `res/raw/gost_russian_trusted_root_ca.pem` |

### 2.3. Как проходит проверка сертификата при включённом плагине

**dart:io (Flutter-стек: dio, http, Image.network, cached_network_image).**
При старте `GostRootCa.enable()` устанавливает `HttpOverrides.global` —
фабрику `HttpClient`, через которую создаются все HTTP-клиенты dart:io.
Контекст `SecurityContext(withTrustedRoots: true)` дополняется корнем
Минцифры (`setTrustedCertificatesBytes`). Проверка сертификата и
hostname выполняется движком dart:io как обычно, с расширенным списком
корней. Если хост-приложение уже установило свой оверрайд (дебаг-прокси,
логирование), он не затирается, а становится звеном цепочки; явно
переданный библиотекой `SecurityContext` уважается (наш подставляется
только вместо `null`).

**iOS URLSession (нативный REST, сетевые вызовы плагинов и SDK).**
Плагин свиззлит фабричные конструкторы `NSURLSession` и `+[NSURLSession
sharedSession]` при регистрации (до старта Dart). Делегат **каждой**
создаваемой сессии оборачивается в прокси. Прокси перехватывает **только**
server trust challenge:
1. сертификат оценивается стандартно (`SecTrustEvaluateWithError`);
2. если стандартная оценка **прошла** — плагин не вмешивается, челлендж
   уходит оригинальному делегату (pinning/mTLS хоста работают как без
   плагина);
3. если **не прошла** — на копии trust (`SecTrustCreateWithCertificates`
   с теми же политиками) добавляются якоря Минцифры
   (`SecTrustSetAnchorCertificates` + `SecTrustSetAnchorCertificatesOnly(false)`,
   т.е. системные корни сохраняются) и оценка повторяется;
4. если с якорем цепочка сошлась — соединение пропускается
   (`.useCredential`); во всех остальных случаях челлендж уходит
   оригинальному делегату или в default handling.

Копия trust строится только с оригинальными политиками (включая
hostname-проверку); если копию построить нельзя — прозрачный отказ
(«не доверено»), т.е. в сторону fail-closed.

**iOS WKWebView (WebView).** Сетевой стек WebKit работает в отдельных
системных процессах, поэтому перехват возможен только на делегатном
уровне: свиззлится `setNavigationDelegate:`, делегат оборачивается в
прокси, который на server trust challenge отвечает так же, как в п. выше.

**Android (WebView, HttpURLConnection, OkHttp).** Доверие настраивается
декларативно через Network Security Config: `<trust-anchors>` = системные
корни + корень Минцифры для всех доменов приложения. Метод `enable()`
на Android — no-op.

**Особенность iOS ATS.** Помимо проверки доверия, Apple требует политику
ATS: TLS 1.2+, PFS, размер ключа, и — главное — сходимость цепочки к
корню, встроенному в ОС или установленному пользователем/MDM. Якоря,
подставленные через `SecTrustSetAnchorCertificates`, ATS **не учитывает**,
поэтому без исключения в `Info.plist` гостовские цепочки блокируются ещё
до проверки доверия. По данным разработчика (проверено на устройстве),
работает только глобальный `NSAllowsArbitraryLoads=true`; более узкие
исключения (`NSExceptionDomains`, `NSAllowsArbitraryLoadsInWebContent`)
для цепочек Минцифры неэффективны.

### 2.4. Идемпотентность и отказы

- Повторные `enable()` безопасны: dart-оверрайд не наслаивается сам на
  себя; на iOS свиззлы ставятся один раз, якоря переустанавливаются.
- Если PEM не удалось распарсить на iOS — в лог пишется сообщение
  (`NSLog`, без чувствительных данных), якоря пустые, прокси прозрачен
  (fail-closed для гостовских цепочек).
- Если PEM не удалось добавить в dart:io — ошибка молча игнорируется,
  стандартный SSL продолжает работать (fail-open к стандартным корням).
- `enable({certPem})` позволяет хост-приложению передать **любой** PEM;
  на iOS он через MethodChannel переопределяет встроенный якорь.

## 3. Где и в какую сторону меняется безопасность приложения

Оценка изменения по векторам. «↑» — риск растёт, «↓» — снижается,
«—» — не меняется.

### 3.1. Модель доверия (↑)

| Аспект | Было | Стало |
|---|---|---|
| Доверенные корни | Только системные (Apple/Android) | Системные + **Russian Trusted Root CA** |
| Область применения | — | Все домены, все стеки, весь срок жизни процесса |

Добавление любого корневого CA — это классическое расширение модели
доверия: любой, кто получит сертификат от НУЦ Минцифры (или её
подчинённых УЦ, или скомпрометирует их) на целевой домен, сможет
перехватывать и подменять HTTPS-трафик приложения. Применительно к
Russian Trusted Root CA:
- корень государственный, выпускает сертификаты большому числу
  коммерческих и государственных организаций — широкая зона доверия;
- решение о доверии фактически принимает поставщик плагина (встроенный
  PEM) или хост-приложение (параметр `certPem`), а не пользователь;
- плагин **не** предоставляет механизм «доверять только доменам .рф /
  госресурсам» — корень доверен всем доменам.

Направление изменения: **риск MITM растёт**; величина риска ограничена
тем, что доверяется один конкретный CA (а не «любой сертификат»), и что
стандартные корни не удаляются.

### 3.2. iOS: отключение ATS (`NSAllowsArbitraryLoads=true`) (↑↑)

Это единственное изменение, которое ослабляет безопасность **всего**
трафика приложения, а не только гостовских цепочек:

| Что разрешает | Последствие |
|---|---|
| HTTP-соединения с любым хостом в открытом виде | Трафик, который ATS раньше блокировала, теперь уходит незашифрованным (если хост-код это допустит) |
| Снятие требований ATS к TLS (TLS 1.2+, PFS, размер ключа) для новых соединений | Возможны соединения со слабыми параметрами TLS/сертификатами |

Важные оговорки:
- ATS не отключает проверку TLS как таковую для HTTPS: валидация цепочки
  и hostname для https-соединений продолжает работать (с якорями плагина);
- риск реализуется только если приложение само обращается к HTTP-ресурсам
  или допускает их в WebView (mixed content);
- глобальный характер исключения противоречит принципу наименьших прав;
- дополнительный внебезопасностный риск: `NSAllowsArbitraryLoads` требует
  обоснования при ревью в App Store и может привести к отклонению.

Направление изменения: **риск конфиденциальности/целостности трафика
растёт**; это самый весомый аргумент против использования плагина на iOS
без отдельного решения ИБ.

### 3.3. Глобальные перехваты (↑)

| Механизм | Область | Риски |
|---|---|---|
| `HttpOverrides.global` | Все `HttpClient` dart:io в приложении | Влияет на код, который полагается на дефолтный контекст; цепочка оверрайдов усложняет расследование сетевых проблем |
| Method swizzling `NSURLSession`/`WKWebView` | Все сессии/WebView в процессе, включая созданные другими плагинами | Конфликт с другими SDK, тоже свиззлящими эти методы; `URLSession.shared` заменён на отдельную сессию с `.default`-конфигом (тонкое изменение поведения); ошибка прокси-логики может затронуть чужие челленджи |
| Network Security Config (Android) | Все нативные стеки, все домены | При наличии собственного NSC хост-приложения конфиги **не объединяются** — конфиг хоста побеждает, корень Минцифры молча пропадает (риск доступности, не конфиденциальности) |

Компенсаторы в коде: прокси перехватывает только server trust challenge,
все остальные вызовы прозрачно пересылаются оригинальному делегату;
`respondsToSelector`/`forwardingTarget` повторяют схему TrustKit; геттер
`navigationDelegate` возвращает делегат хоста (не ломает identity-сравнения).

Направление изменения: **риск функциональных сбоев и конфликтов растёт**,
прямого роста уязвимости не создаёт, но увеличивает непредсказуемость
процесса.

### 3.4. Что сохраняется без изменений (—)

| Гарантия | Как обеспечивается |
|---|---|
| Стандартная проверка TLS остаётся первой | iOS: сначала `SecTrustEvaluateWithError` без якорей; dart:io: системные корни остаются в контексте; Android: `<certificates src="system"/>` в тех же trust-anchors |
| Проверка hostname не ослабляется | iOS: копия trust строится с оригинальными политиками; dart:io и Android: hostname-проверка не затрагивается |
| SSL-pinning и mTLS хост-приложения | iOS: челленджи, не относящиеся к server trust (Basic auth, client cert), и server trust при успешной стандартной оценке уходят оригинальному делегату; Dart-сторона: явно переданный `SecurityContext` не подменяется |
| Нет «доверия всему подряд» | Якоря добавляются (`AnchorCertificatesOnly=false`), системные корни не удаляются; плагин никогда не возвращает `.useCredential` без успешной оценки |
| Чувствительные данные не логируются | Единственный `NSLog` — при ошибке парсинга PEM |
| Ключи/сертификаты не покидают устройство | PEM встроен в бинарь; обмен с Dart — только через внутренний MethodChannel |

### 3.5. Жизненный цикл и доступность (↑)

| Сценарий | Последствие |
|---|---|
| Ротация корня Минцифры | Нужно обновить **все три** копии PEM; при пропуске хотя бы одной гостовские цепочки молча перестают работать |
| Истечение срока (27.02.2032) | Гостовские ресурсы недоступны до обновления плагина |
| Неверный PEM на iOS | fail-closed: плагин прозрачен, гостовские сайты не работают |
| Неверный PEM в dart:io | fail-open: стандартный SSL работает, гостовские сайты не работают |
| Собственный NSC у хоста (Android) | Конфиг хоста выигрывает мердж — корень Минцифры пропадает без ошибок |

Направление изменения: **риск доступности растёт** (тихие отказы),
конфиденциальность не страдает.

### 3.6. Поверхность атаки на сам механизм (—/↑)

- `enable(certPem:)` — публичный API: любой код внутри приложения
  (включая вредоносную или скомпрометированную библиотеку) может добавить
  произвольный доверенный корень на всех платформах. Метод канала
  `gost_root_ca` доступен только внутри процесса, но не защищён от
  доверенного кода приложения.
- `static var anchorCertificates` (iOS) — изменяемое глобальное состояние;
  обновляется из метода канала; теоретический риск гонки при обращении с
  других очередей (в практическом сценарии маловероятен).
- Сами свиззлы устанавливаются при регистрации плагина — **до** старта
  Dart, т.е. независимо от вызова `enable()`. Для отдела ИБ это важно:
  факт установки перехвата не управляется конфигурацией приложения.
- Обработка ошибок в dart:io части молчалива (пустой `catch`) — проблемы
  интеграции сложно диагностировать.

Направление изменения: **поверхность атаки «внутри процесса» растёт**
слабо; удалённого вектора нет, т.к. механизм не обрабатывает внешние
данные (единственные входы — собственный PEM и данные челленджей TLS).

### 3.7. Непокрытые сценарии (для полноты)

- iOS background-сессии (`URLSessionConfiguration.background`) — работают
  только пока приложение живо;
- `SFSafariViewController` / Chrome Custom Tabs — системные браузеры в
  отдельных процессах, нужен установленный на устройстве корень;
- task-specific делегаты (iOS 15+) — server trust может уйти напрямую
  `task.delegate`, минуя прокси сессии;
- нативные сессии, созданные до регистрации плагинов.

Эти случаи не ослабляют безопасность (там работает стандартная проверка),
но означают неполноту решения.

## 5. Выводы

1. Механизм технически аккуратен: валидация TLS не отключается,
   добавляется ровно один корень, pinning/mTLS и проверка hostname
   сохраняются, чувствительные данные не логируются.
2. Принципиальные решения, которые должен принять отдел ИБ:
   - **доверие к корню НУЦ Минцифры для всего трафика приложения**
     (риск R1) — по сути это выбор доверенного поставщика TLS-сертификатов;
   - **отключение ATS на iOS** (риск R2) — самое сильное ослабление,
     затрагивает не только гостовские цепочки.
3. Если гостовские ресурсы приложению не нужны — плагин не использовать.
4. Если нужны — целесообразно сочетать с рекомендациями раздела 6.

## 6. Рекомендации по снижению рисков

**Обязательные (перед выпуском):**
1. **Решение ИБ по ATS**: если продукт не работает с HTTP-ресурсами,
   оценить возможность выпуска без `NSAllowsArbitraryLoads` (проверить,
   не появились ли более узкие варианты ATS-исключений для цепочек
   Минцифры в новых версиях iOS); при выпуске с глобальным исключением —
   зафиксировать обоснование и срок пересмотра.
2. **Контроль встроенного корня**: настроить процедуру обновления всех
   трёх копий PEM при ротации НУЦ Минцифры; проверять актуальность
   отпечатка при каждом релизе (автотест на сверку хэша сертификата с
   эталоном с gosuslugi.ru/crt).
3. **Исключить произвольный `certPem` из внешнего ввода**: `enable()`
   должен вызываться только с константой из кода, не из конфигурации
   сервера/удалённого обновления.
4. **Проверка pinning/mTLS на тестах**: регрессионные тесты на то, что
   с включённым плагином pinning-библиотеки продолжают работать
   (пример — тесты в `gost_root_ca/test/`).

**Желательные (снижение области действия):**
5. **Сужение области доверия** вместо глобального:
   - iOS: для своих сессий можно вызывать `SecTrustSetAnchorCertificates`
     только там, где нужны гостовские цепочки (плагин глобален по
     необходимости — оценить, нужна ли глобальность);
   - Android: если у хост-приложения есть свой NSC, добавить корень
     Минцифры в свой конфиг (`tools:replace`) и, по возможности, ограничить
     `<trust-anchors>` набором нужных доменов через `<domain-config>`;
   - dart:io: библиотекам, не работающим с гостовскими ресурсами, передавать
     собственный `SecurityContext` (плагин его уважает).
6. **Мониторинг конфликтов**: при добавлении SDK, которые свиззлят
   `NSURLSession` или ставят `HttpOverrides.global`, — проверять совместную
   работу (риск R3).
7. **Диагностируемость**: рассмотреть логирование события «соединение
   принято по якорю Минцифры» (уровень debug, без данных трафика) для
   расследований.
8. **Периодический пересмотр**: после каждой мажорной версии iOS/Android
   перепроверять актуальность ATS-вывода и непокрытых сценариев
   (раздел 3.7).

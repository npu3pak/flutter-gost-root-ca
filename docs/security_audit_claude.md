# Аудит информационной безопасности: gost_root_ca

**Объект:** Flutter-плагин `gost_root_ca` (пакеты `gost_root_ca`, `gost_root_ca_ios`, `gost_root_ca_android`) — механизм доверия корню НУЦ Минцифры России.
**Репозиторий:** `flutter-gost-root-ca`, ветка `fix/ios-review-leftovers`, коммит `02b07eb`.
**Дата:** 19.08.2026.
**Метод:** статический анализ исходного кода (Dart, Swift, Kotlin, манифесты, NSC), сверка встроенного сертификата с официальным дистрибутивом. Динамическое тестирование на устройствах и аудит инфраструктуры НУЦ в объём не входили.

---

## Кратко

Плагин добавляет корневой сертификат «Russian Trusted Root CA» (НУЦ Минцифры России) в доверенные якоря **всех** сетевых стеков приложения: dart:io (dio/http/картинки), iOS `URLSession` и `WKWebView`, Android-стек и WebView. Стандартная проверка TLS (цепочка, срок, hostname) **не отключается** — добавляется ещё один доверенный корень. Встроенный сертификат во всех трёх копиях подлинный (SHA-256 совпадает с дистрибутивом gu-st.ru).

**Главный эффект для ИБ:** доверие расширяется **глобально для всех доменов**, а не только для «гостовских» хостов. Удостоверяющий центр, не входящий ни в одну публичную root-программу (Apple/Google/Mozilla/Microsoft), без Name Constraints и без обязательного Certificate Transparency, получает техническую возможность выпускать принимаемые приложением сертификаты на любой хост, включая собственный бэкенд. На iOS дополнительно требуется ослабление ATS, которое снижает безопасность *всего* трафика приложения, а делегатный SSL-pinning на iOS обходится для цепочек Минцифры. Критических ошибок реализации не найдено; основные риски — архитектурные и управляемые конфигурацией (скоупинг по доменам, узкое ATS-исключение).

## 1. Описание механизма для отдела ИБ

### 1.1 Назначение

Сайты с поддержкой ГОСТ-TLS (www.sberbank.ru, госсервисы) используют цепочки сертификатов, замыкающиеся на корень НУЦ Минцифры, которого нет в системных хранилищах iOS и Android. Без плагина такие соединения завершаются ошибкой проверки сертификата (`-1202` / `ERR_CERT_AUTHORITY_INVALID`). Плагин делает этот корень доверенным во всех путях, по которым приложение ходит в сеть, не требуя установки профиля/сертификата на устройство пользователя.

### 1.2 Встроенный сертификат

| Параметр | Значение |
|---|---|
| Subject / Issuer | C=RU, O=The Ministry of Digital Development and Communications, CN=Russian Trusted Root CA (самоподписанный) |
| Ключ / подпись | RSA 4096, sha256WithRSAEncryption, serial 1000 |
| Срок действия | 01.03.2022 — 27.02.2032 |
| Расширения | BasicConstraints CA:TRUE, **pathlen 4**; KeyUsage: certSign, cRLSign, digitalSignature; **Name Constraints отсутствуют**; EKU не ограничен |
| SHA-256 | `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31` |
| Проверка подлинности | Все три копии в репозитории побайтно совпадают между собой и с `russian_trusted_root_ca_pem.crt`, скачанным с gu-st.ru (официальный дистрибутив Госуслуг) в день аудита |
| Где хранится | `gost_root_ca/lib/src/gost_root_cert.dart`, `gost_root_ca_ios/ios/Classes/GostBuiltinRootCert.swift`, `gost_root_ca_android/android/src/main/res/raw/gost_russian_trusted_root_ca.pem` |

### 1.3 Компоненты и точки применения

| Компонент | Поверхность | Механизм | Когда активируется |
|---|---|---|---|
| `gost_root_ca` (Dart) | dart:io: dio, http, `Image.network`, cached_network_image | `HttpOverrides.global = GostHttpOverrides`: каждому `HttpClient` без явного контекста подставляется `SecurityContext(withTrustedRoots: true)` + PEM Минцифры. Существующий оверрайд хоста сохраняется в цепочке; явно переданный `SecurityContext` не подменяется | Вызов `GostRootCa.enable()` (явный opt-in в Dart) |
| `gost_root_ca_ios` (Swift) | `URLSession` (все сессии, включая `URLSession.shared`), `WKWebView` (в т.ч. webview_flutter) | Method swizzling: `+sessionWithConfiguration:`, `+sessionWithConfiguration:delegate:delegateQueue:`, `+sharedSession`, `-[WKWebView setNavigationDelegate:]`/геттер. Делегат оборачивается в прокси. Прокси обрабатывает только ServerTrust-челлендж: 1) стандартная `SecTrustEvaluateWithError`; 2) если не прошла — копия trust с якорем Минцифры (`SecTrustSetAnchorCertificatesOnly(false)`, т.е. системные корни + Минцифры); 3) успех → `useCredential`, иначе челлендж уходит оригинальному делегату / default handling. Политики (в т.ч. SSL-политика с hostname) копируются — проверка имени хоста сохраняется | **Автоматически при регистрации плагина** (`GeneratedPluginRegistrant`), до старта Dart. `enable(certPem:)` лишь переустанавливает якорь |
| `gost_root_ca_android` (Kotlin + ресурсы) | Весь нативный стек: WebView (в т.ч. webview_flutter), HttpURLConnection, OkHttp и др. | Network Security Config (`base-config`): `<certificates src="system"/>` + `@raw/gost_russian_trusted_root_ca`. Атрибут `android:networkSecurityConfig` вливается в `<application>` хоста при мердже манифестов. Cleartext не включается, debug-overrides нет, пользовательские CA не добавляются | **Автоматически при сборке** (манифест-мерджер). `enable()` — no-op. Если у хоста свой NSC — конфиг плагина замещается целиком |

### 1.4 Что механизм не делает

- Не отключает и не ослабляет проверку цепочки, срока действия, имени хоста; не использует `badCertificateCallback`, `SecTrustSetAnchorCertificatesOnly(true)` и аналогичные «принять всё» паттерны.
- Не трогает не-trust челленджи (Basic/NTLM, клиентские сертификаты mTLS) — они уходят оригинальному делегату как раньше.
- Не собирает и не передаёт данные, не пишет в лог содержимое запросов (единственный `NSLog` — ошибка парсинга PEM). `PrivacyInfo.xcprivacy` пуст и корректен.
- Не покрывает системные браузеры (SFSafariViewController / Custom Tabs), фоновые iOS-сессии, task-specific делегаты iOS 15+, сессии, созданные до регистрации плагинов.

## 2. Где и в какую сторону меняется безопасность

Обозначения: ▼ снижение, ═ без изменений, ▲ повышение относительно типичной альтернативы.

| Область | Напр. | Что именно меняется |
|---|:-:|---|
| Множество доверенных CA (все платформы, все стеки) | ▼ | К ~140 публичным корням добавляется один, не прошедший публичных root-программ, без Name Constraints, с pathlen 4 (подчинённые УЦ). Любой сертификат, выпущенный этой иерархией на *любой* домен (включая ваш API, OAuth-провайдеров, CDN), будет принят. Выпуск под этим корнем не обязан попадать в CT-логи — мисс-выпуск не обнаруживается мониторингом CT |
| Отзыв сертификатов | ▼ | dart:io (BoringSSL) и Android по умолчанию не проверяют CRL/OCSP; iOS — best-effort. Для публичных CA риск компенсируется CT и коротким сроком жизни сертификатов; для цепочек Минцифры таких компенсаций нет |
| iOS: App Transport Security | ▼▼ | Обязательное исключение в Info.plist. Рекомендуемый в README и используемый в example `NSAllowsArbitraryLoads=true` отключает ATS для **всего** приложения: разрешаются plain-HTTP, TLS < 1.2, наборы шифров без PFS, слабые ключи/подписи. Даже узкий вариант (`NSExceptionDomains` + `NSExceptionAllowsInsecureHTTPLoads`) разрешает для указанных доменов не только нестандартный якорь, но и http://. Это самое значимое снижение, и оно не зависит от кода плагина |
| iOS: SSL-pinning в делегате URLSession/WKWebView | ▼ | Прокси отвечает `useCredential` **до** вызова оригинального делегата, если цепочка валидна через якорь Минцифры. Пиннинг хоста срабатывает только для цепочек, прошедших стандартную проверку. Сертификат на ваш бэкенд, выпущенный под корнем Минцифры, пройдёт мимо делегатного пиннинга. Android NSC `<pin-set>` и OkHttp `CertificatePinner` не затронуты (пины проверяются после построения цепочки) |
| Скоупинг по доменам | ▼ | Якорь применяется ко всем хостам. Нет allowlist ни на одной платформе, хотя Android NSC поддерживает `<domain-config>`, а на iOS доступен `challenge.protectionSpace.host` |
| Факт включения / управляемость | ▼ | На iOS и Android доверие расширяется самим фактом подключения зависимости (регистрация плагина / мердж манифеста), без вызова `enable()`; выключателя нет |
| Параметр `enable(certPem:)` | ▼ (потенц.) | Позволяет во время выполнения подставить *произвольный* PEM (в т.ч. bundle из нескольких корней) в якоря iOS и dart:io. Если значение придёт из недоверенного источника (remote config, deep link, ответ сервера) — готовый канал внедрения чужого CA. На Android параметр игнорируется — расхождение поведения платформ |
| Проверка цепочки, срока, hostname | ═ | Сохраняется на всех стеках. На iOS политики копируются в проверочный trust; при провале оценки с якорем оригинальный делегат получает нетронутый `SecTrust` |
| mTLS, Basic/NTLM, явный `SecurityContext`, существующий `HttpOverrides` | ═ | Не перехватываются / делегируются как раньше |
| Android cleartext, user-CA, debug-overrides | ═ | NSC плагина их не включает; системные корни сохраняются. Но NSC плагина *замещает* конфиг хоста при конфликте (и наоборот) — требуется ручная сверка итогового конфига |
| Поведение сторонних нативных SDK (iOS) | ═ / регрессии | Глобальный swizzling затрагивает все SDK в процессе (TrustKit, Firebase Perf, Datadog, New Relic тоже свиззлят URLSession). Не уязвимость, но источник трудно диагностируемых регрессий; `URLSession.shared` подменяется на другой экземпляр |
| По сравнению с типичной «обходной» практикой | ▲ | Если альтернатива — `badCertificateCallback = true`, ATS + «принять любой сертификат» и т.п., плагин существенно безопаснее: добавляется конкретный верифицированный корень, а не отключается проверка |

## 3. Находки

### F-1 · High · Глобальное доверие CA вне публичных root-программ без ограничения по доменам

**Суть.** Архитектурный, а не реализационный риск: корень принимается для всех хостов на всех стеках. Сертификат не имеет Name Constraints, допускает 4 уровня подчинённых УЦ; отсутствуют CT и практическая проверка отзыва. Последствие — расширение круга субъектов, способных на технически «валидный» MITM, на оператора этой иерархии и любого, кто получит ключ подчинённого УЦ.

**Где.** `GostSslSwizzler.isTrustedViaGostAnchor`; `gost_network_security_config.xml` (`base-config`); `GostHttpOverrides._buildSecurityContext`.

**Рекомендация.** Принять риск осознанно и задокументировать решение. Технически снизить: Android — перенести якорь из `base-config` в `<domain-config>` с перечнем гостовских доменов; iOS — проверять `challenge.protectionSpace.host` по allowlist до применения якоря; dart:io — либо принять глобальность, либо реализовать per-host логику через `badCertificateCallback` с собственной проверкой цепочки. Предусмотреть API `enable(allowedHosts: [...])`.

### F-2 · High · iOS: требуемое ослабление ATS снижает безопасность всего приложения

**Суть.** README шаг 3 и example используют `NSAllowsArbitraryLoads=true`. Это снимает требования TLS ≥ 1.2, PFS, SHA-256, RSA ≥ 2048 и разрешает http:// для всех соединений `URLSession`/`WKWebView`, а не только для гостовских. Также потребует обоснования при ревью App Store.

**Рекомендация.** Запретить глобальный ключ в продуктовых сборках; использовать `NSExceptionDomains` с `NSIncludesSubdomains` только для гостовских доменов или `NSAllowsArbitraryLoadsInWebContent`, если гостовский трафик только в WebView. Для собственного бэкенда явно оставить ATS (`NSExceptionAllowsInsecureHTTPLoads=false`). Добавить CI-проверку Info.plist. В README поменять порядок: узкий вариант первым, глобальный — с предупреждением.

### F-3 · Medium · iOS: делегатный SSL-pinning хоста обходится для цепочек Минцифры

**Суть.** В `GostSessionDelegateProxy` и `GostNavigationDelegateProxy` ветка «якорь сработал → `useCredential`» выполняется раньше передачи челленджа оригинальному делегату. Если хост пинит свой бэкенд в делегате, а злоумышленник предъявляет сертификат на этот бэкенд, выпущенный под корнем Минцифры, пиннинг не вызывается. Утверждение README «SSL-pinning продолжает работать» верно только для цепочек, прошедших стандартную проверку.

**Рекомендация.** Минимум — честно описать в README. Лучше — при наличии у оригинального делегата обработчика челленджа передавать ему челлендж и после успешной оценки с якорем (якоря уже установлены в trust, повторный `SecTrustEvaluate` у хоста пройдёт, а его пины применятся), либо дать хук/allowlist. Совместно с F-1: скоупинг по доменам закрывает и этот сценарий.

### F-4 · Medium · Активация без opt-in и без выключателя

**Суть.** На iOS свиззлы и встроенный якорь ставятся в `register(with:)`; на Android NSC вливается при сборке. `GostRootCa.enable()` нужен только для dart:io. Нет `disable()`, нет флага сборки. ИБ не может ограничить эффект или отключить по фиче-флагу.

**Рекомендация.** Задокументировать явно в шапке README. Рассмотреть режим «свиззлы ставятся при регистрации, но якорь пустой до `enable()`» — код это уже поддерживает (`installSwizzles()` отдельно от `setAnchorCertificates`). На Android альтернативы без правки хоста нет — зафиксировать.

### F-5 · Medium · `enable(certPem:)` — runtime-канал подстановки произвольного CA; платформы расходятся

**Суть.** Параметр без ограничений переустанавливает якоря iOS и dart:io (парсер принимает PEM-bundle — все сертификаты становятся якорями). На Android игнорируется. Риск — только если значение не «зашито» в код; но API об этом не сигнализирует.

**Рекомендация.** В документации пометить параметр как «только константы из кода, никогда из сети/конфига». Рассмотреть проверку: принимать только сертификаты с CA:TRUE, логировать отпечаток принятого якоря. Либо убрать параметр из публичного API (ротация через обновление пакета). Для Android — задокументировать, что параметр не действует.

### F-6 · Low · Глобальный swizzling: конфликты и побочные эффекты

**Суть.** Подмена `+sharedSession` на собственный экземпляр, оборачивание делегатов всех сессий и WKWebView. Возможны конфликты порядка со свиззлерами APM/TrustKit, поломка identity-сравнений `session === URLSession.shared`, iOS-обновления, меняющие внутреннюю цепочку вызовов конструкторов. Статическое поле `anchorCertificates` читается из делегатных очередей и пишется из главного потока без синхронизации (гонка при повторном `enable` с другим PEM).

**Рекомендация.** Регрессионные тесты на реальном устройстве при каждом мажорном iOS; сделать `anchorCertificates` immutable после первой установки или защитить `os_unfair_lock`; в README перечислить известные свиззлящие SDK.

### F-7 · Low · Цепочка поставки и ротация сертификата

**Суть.** README предлагает git-зависимость без `ref:` — сборка подтягивает текущий `main`. Корень хранится в трёх копиях, синхронизация ручная; CI-теста на равенство отпечатков нет. Обновление корня возможно только релизом приложения.

**Рекомендация.** Пиновать `ref:` на коммит/тег, вендорить в монорепо; добавить тест, сверяющий SHA-256 трёх копий между собой и с константой; указать отпечаток в README. Назначить владельца процесса ротации.

### F-8 · Info · Неточная формулировка в README

**Суть.** «Подделать соединение сложнее не становится» — верно относительно «отключить проверку», но неверно относительно baseline: множество субъектов, способных выпустить принимаемый сертификат, расширяется (см. F-1, F-3).

**Рекомендация.** Переформулировать: «проверка не отключается; доверие расширяется на один дополнительный УЦ, см. раздел о рисках».

### Что реализовано корректно

- Сертификат подлинный, идентичен во всех копиях и официальному дистрибутиву.
- Проверка hostname сохранена (политики копируются в проверочный trust); при неуспехе с якорем оригинальному делегату отдаётся неизменённый `SecTrust`.
- Системные корни не вытесняются (`AnchorCertificatesOnly=false`, `src="system"`, `withTrustedRoots: true`).
- Не-trust челленджи, явный `SecurityContext`, существующий `HttpOverrides` — не перехватываются/делегируются; идемпотентность `enable()`; прокси не оборачивается повторно.
- Android: cleartext не включён, debug-overrides и user-CA отсутствуют.
- Нет сбора данных, сетевых вызовов плагина, секретов в репозитории; `local.properties`/`.idea` не отслеживаются git.

## 4. Рекомендации (по приоритету)

1. **ATS (iOS):** запретить `NSAllowsArbitraryLoads` в релизных сборках; только `NSExceptionDomains` для гостовских доменов или `NSAllowsArbitraryLoadsInWebContent`. Проверка в CI.
2. **Скоупинг по доменам:** Android — `<domain-config>` вместо `base-config`; iOS — allowlist хостов перед применением якоря; API `enable(allowedHosts:)`. Одновременно закрывает сценарий обхода пиннинга (F-3).
3. **Пиннинг собственного бэкенда** реализовать так, чтобы он не зависел от делегатного перехвата: Android NSC `<pin-set>` / OkHttp `CertificatePinner`; на iOS — пиннинг, выполняемый и после успешной оценки с якорем (или allowlist, исключающий ваш бэкенд из действия якоря).
4. **Политика использования `certPem`:** только константы в коде; задокументировать, рассмотреть удаление из публичного API.
5. **Цепочка поставки:** пиновать версию плагина, тест на отпечатки, владелец ротации.
6. **Документация:** исправить формулировку про «не становится проще подделать»; явно описать, что на iOS/Android доверие включается самим подключением зависимости; перечислить обходимые сценарии пиннинга.
7. **Мониторинг:** логирование (без PII) факта срабатывания ветки «принято через якорь Минцифры» с хостом, чтобы ИБ видела, на какие домены реально применяется расширенное доверие.
